# Noty 架构调研报告：滴答清单任务便签与双向状态同步

- 状态：**方案已修订，待实现与端到端验收**。
- 日期：2026-10-14；修订依据为本次源码审计、官方文档与真实账号只读请求。
- 研究版本：Noty `179a6da7bcbd95e1c626d0ba27151541b73d3038`；本机 `@suibiji/dida-cli` 为 `0.1.14`。
- 工作区边界：原有 `build.sh` 修改和未跟踪目录存在。本次只修订本文，未修改应用代码、账号任务或发布产物。
- 核心结论：**以 Noty 浮动便签承载滴答任务可行。第一期交付任务展示与完成状态同步；取消完成须先通过接口验证。原方案的全量读取、缺失删除、行号映射和超时回滚规则已撤销。**

## 1. 用户得到什么

在 Mac 上，滴答清单的任务像 Noty 便签一样常驻屏幕边缘；展开、拉出和置顶沿用现有交互。用户不用反复切回滴答客户端，就能查看和完成任务。

第一期的产品路径：

1. 设置 → 滴答清单 → 连接账号。支持使用已有 dida-cli 登录，或粘贴个人 API Token；认证信息进入 macOS Keychain。
2. 默认选中收集箱，也可选择其他任务清单；点击“创建任务便签”。一条便签可聚合多个清单。
3. 便签先显示未完成任务。滴答手机端新增、改名或完成任务，Noty 下一轮成功读取后更新。
4. 在 Noty 点击任务复选框，立即显示“正在确认”；确认成功后打勾，并移入底部“近期完成”。
5. 断网或认证失效时保留已有内容，明确显示状态和最近成功更新时间，恢复后自动读取。

示意内容：

```text
滴答 · 收集箱 + 工作                 已更新 16:30

收集箱
□ 买牛奶

工作
□ 写周报

近期完成 · 1
✓ 寄快递
```

这是内容与状态示意，视觉沿用 Noty 纸张、颜色和字体。每条任务允许长标题换行和选择复制；不显示 taskId、etag 或请求路径。存在多个清单时按清单分组，避免任务来源和排序混淆。

### 1.1 已确定的产品范围

| 项目 | 第一期决策 |
|---|---|
| widget 的含义 | **Noty 浮动任务便签**，使用现有窗口与边缘便签外壳 |
| 文字与任务结构 | 滴答维护；Noty 只读展示 |
| 在 Noty 完成任务 | 必须实现，服务端确认后收敛 |
| 在滴答完成或恢复任务 | Noty 读取后对齐；恢复任务的读取不依赖 Noty 是否提供取消按钮 |
| 在 Noty 取消完成 | 验证通过后提供；未通过则已完成复选框不可反向操作，并提示“请在滴答中恢复任务” |
| 已完成记录 | 默认展示最近 24 小时，位于底部，可折叠或隐藏；不加载全部历史 |
| 便签属性 | 保留自定义标题、颜色、置顶、窗口尺寸、位置和本地排序 |
| 删除任务便签 | 只解除本机展示，绝不删除滴答任务；沿用 Noty 删除撤销窗口 |
| 多台 Mac | 每台各自连接、各自创建便签，任务状态通过滴答对齐；便签绑定不经 iCloud 传播 |

本文中的“双向”指**滴答状态进入 Noty，Noty 的完成操作进入滴答**。不包含文字、任务创建或删除的双向编辑。取消完成未通过验收时，交付说明必须明确该边界。

### 1.2 后续范围

正文编辑、创建或删除滴答任务、子任务编辑、优先级和日期修改另立方案。后续编辑也必须按稳定 taskId 操作，不使用标题相似度猜测任务身份。

macOS 原生桌面小组件另立项目：它需要 WidgetKit 扩展、AppIntent 和共享数据设计。Apple 明确说明扩展不持续运行，刷新受系统预算控制，不能沿用本文的秒级轮询承诺。[Apple 刷新机制](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date)、[交互能力](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)。

## 2. 已验证事实与待验证边界

### 2.1 API 证据

本次请求基址为 `https://api.dida365.com/open/v1`。请求只读取信息，输出仅保留结构、数量和状态分布，没有输出 token、任务标题或账号标识。

| 请求 | 本次实际结果 | 可以得出的结论 |
|---|---|---|
| `GET /project` | HTTP 200，数组，10 个清单 | 清单列表读取可用；不证明每个清单都可写 |
| `GET /project/inbox/data` | HTTP 200，对象包含 `columns`、`tasks`；19 条任务，均为 status=0 | 收集箱未完成任务读取可用；本次对象没有 `project`，解码不能强制要求该字段 |
| `POST /task/filter`，`{"projectIds":["inbox"],"status":[0]}` | HTTP 200，19 条，与上项任务 ID 集合一致 | 正确请求字段为 `projectIds` |
| 同一路径，status=[0,2] | HTTP 200，200 条：19 条未完成、181 条已完成 | 混查结果不是完整历史任务集合 |
| 同一路径，status=[2] | HTTP 200，200 条已完成；与混查已完成集合不同 | “本轮没有返回”不能作为删除证据 |
| 上述任务读取的排序 | 返回序列不是 sortOrder 升序 | 必须显式定义显示排序，不能把接口返回顺序等同于滴答手工顺序 |

官方文档明确：`/task/filter` 和 `/task/completed` **最多返回 200 条**。filter 的日期条件针对任务 startDate，completed 的日期条件针对 completedTime，不能互换。[滴答官方 OpenAPI](https://developer.dida365.com/docs/openapi.md#filter-tasks)。

以下属于待验证项，不得写成“全部实测通过”：

- 普通清单以及超过 200 条未完成任务的 `/project/{projectId}/data` 完整性；本次只验证了收集箱 19 条。
- `/task/completed` 的实际返回、时间边界、截断后的补全能力。
- 完成后的单任务回读、权限失败与已移出清单的返回语义。
- `POST /task/{taskId}` 是否接受顶层 status=0，并真正恢复任务；Update Task 参数表未列出该字段。
- 重复任务完成后的下一实例、共享清单权限，以及不同客户端的排序一致性。
- Noty 与手机之间的实际到账延迟、耗电和限流表现。

原方案附录曾记录创建、完成和删除测试任务，但本轮没有复现这些写请求。它们保留为历史报告陈述，不作为本轮端到端验收证据。

## 3. 最小架构

```text
滴答云端
  ├─ GET /project/{projectId}/data      未完成任务候选来源
  ├─ POST /task/completed              近期完成，严格检测截断
  ├─ GET /project/{projectId}/task/{taskId}  单项确认
  └─ POST .../complete                用户明确点击后写入
           │
     TickTickClient（URLSession、Codable、HTTP 错误分类）
           │
     TickTickSync（串行状态、读取、合并、确认与调度）
       ├─ TickTickBindings（本机清单绑定）
       ├─ 加密任务缓存（任务快照与未确认操作）
       └─ NoteStore（现存便签的文本快照，用于搜索与导出）
           │
     TickTickTaskListView（按 taskId 渲染和交互）
           │
     原有边缘便签 / FloatingNote / LibraryWindow
```

只增加上述实际职责，不引入通用同步框架、服务端或第三方网络依赖。Foundation、SwiftUI、Security、CryptoKit 与项目现有 SQLite 能力足够。

任务列表使用 SwiftUI 的真实 Button 或 Toggle，通过 taskId 发出操作；支持键盘焦点、Space 操作、VoiceOver 标签、复制标题与长标题换行。普通便签继续使用现有 NoteTextView。

## 4. 数据身份、缓存与持久化

### 4.1 便签类型必须可靠持久化

在 Note 和 SQLite notes 表增加最小 `source` 字段：`local` 或 `ticktick`。沿用现有 `Store.migrate()` 加列模式，旧行默认 local；缺失字段的旧导入文件按普通便签处理。未知类型不得静默降为可编辑 local。

这个字段解决真实故障：如果仅靠绑定 JSON 判断类型，文件丢失或损坏会使任务快照被当作普通便签，进而允许编辑和 iCloud 同步。采用字段后，配置损坏时仍能展示快照，并显示“连接配置异常”；禁止任务写入和普通正文编辑。

不增加任务业务表，不修改现有 body 加密方式。此处是待实现设计；数据库迁移与实际执行必须经过工程安全流程，本文修订没有操作本机数据库。

### 4.2 绑定与任务缓存

绑定文件 `ticktick-bindings.json` 只包含版本、noteId 和选中清单，不含 token、任务正文或完整任务标题。例如：

```json
{
  "version": 1,
  "bindings": [
    {"noteId":"<NOTE_UUID>","projectIds":["inbox","<PROJECT_ID>"]}
  ]
}
```

- 首次创建采用新便签，不把已有普通便签直接转换，避免覆盖本地正文和遗留 iCloud 副本。
- 绑定文件严格校验版本、重复 ID 和 Note.source；读取失败保留原文件并进入配置异常态，禁止按“空绑定”继续运行。
- 文件保存使用原子替换，错误必须反馈；缓存未保存成功不能显示“已保存”。
- 结构化任务快照与未确认操作存入单个加密缓存文件，复用项目现有 Crypto 能力；缺失缓存时展示 Note.body 的只读快照，首次成功读取前禁用勾选。
- 重启后未确认操作只回读，不自动重放写请求。认证更换账号前暂停旧任务、隔离旧绑定和缓存，完成新账号校验后重新选择清单。

任务身份为账号连接上下文中的 taskId，projectId 是当前地址信息；便签、账号连接与绑定变更带 generation。多个便签展示同一任务时共享任务状态和未确认操作，不分别发送完成请求。

### 4.3 快照更新规则

Note.body 只是派生文本快照，用于现有搜索、进度、预览和用户导出；不拿行号解析出任务 ID，也不由正文变化触发 API 写入。

新增 NoteStore 的受控快照更新方法：校验便签仍存在且 source=ticktick，仅修改当前对象的 body 和必要时间；保留当下标题、颜色、位置、排序、归档与置顶状态。正文相同时不重写数据库。不使用旧 Note 副本整条 absorb，也不创建失踪便签。

导出任务便签是普通文本快照；导入后成为新的普通便签，不恢复账号绑定、任务身份或未确认操作。数据库读取保留 source，文档导入则显式解除来源，两条边界分别实现和测试。

## 5. 获取任务：完整性优先于集合 diff

### 5.1 未完成任务

以所选清单的去重集合逐个读取 `/project/{projectId}/data`；多个便签复用同一轮结果。收集箱查询使用官方接受的 inbox 别名，写入与单任务回读使用任务返回的实际 projectId。

- 响应必须包含可解码 tasks 数组；不存在 tasks、解码失败或部分清单请求失败，都不能当作空清单。
- 大清单完整性是实施前置验证；官方字段缺少截断标记时，不得仅凭“HTTP 200”认定完整。
- 若无法证明所需清单读取完整，必须显示“列表未完整加载”，明确交付支持范围；不得声称任意规模清单双向同步已完成。
- 不使用混合 status=[0,2] 的 filter 结果作为基准快照；filter 只用于诊断与交叉核对。

### 5.2 近期完成

使用 `/task/completed` 查询最近 24 小时，按完成时间展示。默认每 60 秒读取，用户完成操作和相关缺失确认后按需刷新；该接口仍需实测。

返回 200 条即标记为存在截断风险，不假设“刚好完整”。优先按清单和 completedTime 时间窗口分段读取；相邻窗口包含边界重复时按 taskId 去重。单轮历史补全最多 8 个请求，按时间中点拆分且最小窗口 1 秒；到达预算或最小窗口仍饱和时保留不完整标记，不继续无限拆分。后续轮次续查剩余窗口，同一时间点超过上限时停止补全并明确提示范围。

“近期完成”到期只从展示缓存移除，不调用滴答删除接口。未确认操作、未知完成时间与不完整窗口中的已知记录，不因窗口到期猜测删除；完成确认取得可信时间后再应用 24 小时规则。

### 5.3 已知任务本轮消失

**缺失只触发确认，不直接删除本地行。**

1. 保留已有任务，标为待核实；优先查近期完成结果。
2. 对仍无法分类的任务，用实际 projectId 与 taskId 单项回读。每轮最多确认 4 项，其余保留队列，未确认写操作优先。
3. 读取到 status=2：进入近期完成；status=0：保留未完成；status=-1：移出行动列表。
4. 明确确认任务已不属于所选清单：移出当前展示，不调用删除。
5. 单项 404 先保留待核实，下一轮再确认；两个独立请求均为 404 时可移出当前展示，描述为“已不可访问”，不宣称任务已删除。403、401、超时和 5xx 均不作为删除依据。

历史结果没有该 taskId、窗口不完整或整轮失败时，均维持最后可信状态。对从未读到的任务无法靠单项确认补全，仍受 §5.1 的大清单验收门槛约束。

### 5.4 排序与任务种类

未完成任务按用户选择的清单顺序分组，同组按 sortOrder 升序、taskId 作稳定次级排序；缺少 sortOrder 的任务放组末。这个规则是 Noty 的明确显示策略，是否与滴答手工排序一致需要客户端核对。

近期完成按 completedTime 降序。etag 仅是变更提示；仍比较 title、status、projectId、sortOrder 和任务集合，不能 etag 相同就跳过排序或范围变化。

kind=NOTE 不提供完成按钮；CHECKLIST 首期只展示父任务，不展平子项，其完成语义通过专用测试后开放；重复任务也需验证下一实例行为后开放。未验证类型只读展示并引导到滴答处理，不能使用已经验证的普通任务结论外推。

## 6. 完成操作与并发确认

### 6.1 写入只由用户动作触发

```text
用户点击 taskId 对应复选框
  → 校验便签、连接 generation、当前任务身份与写入能力
  → 持久化未确认操作，成功后显示“正在确认”并禁用该任务重复点击
  → POST /project/{actualProjectId}/task/{taskId}/complete
  → 单任务回读或可信完成查询确认 status=2
  → 更新共享快照，解除 pending，移入近期完成
```

一次操作关联 noteId、taskId、实际 projectId、目标状态、连接/绑定 generation 与发送时间。缓存保存失败则不发送请求。任务标题和行号不参与定位。

### 6.2 状态与失败处理

| 状态 | 行为 |
|---|---|
| idle | 显示已确认状态，可在已验收范围内操作 |
| sending | 即时显示确认中的反馈，禁用同一任务重复点击 |
| awaitingConfirmation | 请求已得到成功响应，等待权威回读；HTTP 成功不等于完成状态已验证 |
| uncertain | 超时、连接中断或无法判定是否已执行；保留 pending，持续回读，不自动重发 |
| confirmed | 回读到目标状态后更新快照并清除 pending |
| rejected | 明确拒绝；显示最后可信状态与错误说明；仍以后续回读校正 |

确认流程最多主动等待 30 秒，超过后显示“结果待确认”，继续在正常轮询中回读。禁止把“10 秒没看到”解释为写入失败，禁止自动补发 completion；重复任务的重放风险尤其需要验证。

远端变化不发出新的写请求，所以不需要靠 pendingEcho 防止正文同步回环。pending 的职责是管理未确认操作、同任务去重和用户反馈。

当存在 pending 时，旧轮询结果不能把反馈退回未完成；新鲜回读若确认目标状态则收敛，若状态不符则保持待确认，直到取得足以解释结果的证据。确认后再次出现远端反向变化，作为新的远端编辑对齐，不自动抢写。

### 6.3 生命周期与乱序响应

网络请求异步执行，状态机使用单一串行执行域；UI 和 NoteStore 更新在主线程。不要直接复制 CloudSync 的同步文件 IO 方式到网络请求。

- 每个清单与同一任务的请求按序应用；绑定、账号或凭据变化立即递增 generation，丢弃旧响应。
- 手动刷新、定时器与激活事件合并，同一读取通道只保留一轮在途请求。
- 便签删除、归档、解除连接或睡眠时停止相应调度；取消请求不等于服务端取消写入，已有 pending 仍按未知结果处理。
- 删除的便签不接受异步响应；撤销删除后恢复绑定并重新读取，不自动重放此前写入。
- 多台设备有并发更改时采用远端最终状态，不承诺跨端事务或绝对实时一致。

### 6.4 取消完成的开放门槛

不得仅从 CLI updateTask 方法推定 status=0 可用。用经用户明确授权的专用测试任务验证：

```text
创建普通测试任务 → 完成 → 权威回读 status=2
→ POST /task/{taskId}（id、projectId、status=0，字段以真实契约为准）
→ 权威回读 status=0 → 手机/网页确认恢复 → 核对标题、日期、子项等未被清空
```

普通、重复和 CHECKLIST 类型分别验证。仅开放已经验证的类型；不能用完整旧任务覆盖更新来掩盖接口不确定性。若请求不支持恢复，第一期保留“在滴答中恢复”入口，不引入未文档化私有接口。

## 7. 调度、认证与状态反馈

### 7.1 调度默认值

| 场景 | 读取规则 |
|---|---|
| 启动、唤醒、展开任务便签、应用激活 | 合并触发一次立即读取 |
| 有任务便签可见 | 未完成任务每 15 秒；近期完成每 60 秒 |
| 任务便签均隐藏 | 每 60 秒 |
| 用户点击“刷新” | 发起一次读取；已有在途请求时合并 |
| 用户完成任务 | 立即写入，随后优先单项确认 |
| 无有效任务便签、断开连接、系统睡眠 | 停止定时读取 |

单请求超时 10 秒；任务确认主动等待上限 30 秒。429 优先遵循 Retry-After；缺少有效值时与网络/5xx 失败一样按 15、30、60、120、300 秒退避，并加入少量抖动。Retry-After 大于 300 秒时照服务端要求等待，不提前重试。成功后恢复场景对应间隔，401 暂停直到凭据更新，403 提示权限不足并停用相关写入。

请求数量按去重清单计算，不按便签数重复发请求。5 秒轮询对 N 个清单约为每分钟 12N 次基础读取，还不包括历史和确认；此前一次请求成功不构成长时间限流证据，所以取消默认 5 秒和“5 秒内必达”承诺。

正常可见状态下，将“下一轮成功读取，目标约 15 秒加网络耗时”作为设计目标；真实延迟必须测量，断网、退避和睡眠不计入这个目标。

### 7.2 认证与隐私

- 个人使用默认支持官方个人 API Token；已有 CLI 用户可选择“使用已有登录”，只读其配置，不修改 CLI 文件。CLI token 的签发者、有效期和权限不能由文件路径推定。
- Noty 接受的 token 保存到 Keychain；绑定、缓存、日志、导出和 iCloud 文件均不得携带 token。
- 更换凭据先暂停请求并切换 generation；不能沿用旧账号的绑定直接写入新账号。
- 认证成功只证明读取权限；写入能力须通过专用任务验收或服务端明确权限证明，实际拒绝必须正常处理。
- token 只发往固定滴答 API 主机；禁止携带认证头跟随跨主机重定向，日志不打印 Authorization 或任务正文。
- 官方 OAuth 当前说明使用 client_secret；PKCE 支持和原生 public-client 方案未验证。已有 noty:// 入口不等于 OAuth 已实现，后续需校验 state、回调、凭据保存及提供方支持。

接入后更新 README 和设置隐私说明：用户启用后，Noty 会向滴答读取任务，并在用户点击时发送完成操作。撤销原 README 中“只有更新检查发生网络请求”的适用范围；默认未连接时不得发滴答请求。[官方认证说明](https://developer.dida365.com/docs/openapi.md#authorization)。

### 7.3 用户能看懂的反馈

标题栏显示：已更新 HH:mm、刷新中、离线、登录已失效、权限不足、列表未完整加载、配置异常。任务行单独显示正在确认或结果待确认。

状态独立于 Note.title 与 Note.body，不能为了更新时间而不断写数据库。允许手动刷新和重新连接。离线时保留内容；完成按钮禁用并解释原因，不做离线写队列。发送后才断网的任务保留未确认状态。

## 8. iCloud 与本机生命周期隔离

任务便签为本机专用展示，source=ticktick 的便签不进入 iCloud 同步计划。隔离覆盖：

1. 本地 notes 输入、远端同 ID 文件、相关 unresolved 与索引项均从本轮决策视图排除；不能只过滤本地 notes，否则远端文件仍会触发 pull 或 deleteRemote。
2. push、pull、adopt、conflict、deleteLocal 和 deleteRemote 执行前再次检查受保护身份。存在未决配置故障时按 source 保护，不根据绑定文件为空解除保护。
3. 创建绑定便签时先可靠保存 source 和绑定，再发布到共享 notes 或启动 CloudSync 可见流程；失败不留下 source=local 的任务快照。
4. 本机删除只删除本机便签，绝不发滴答删除接口。撤销期保留绑定和 pending；恢复后先回读。
5. 旧版本或人工文件留下同 ID 云端副本时，暂停该对象云同步并提示；不自动删除云文件，也不批量清理索引。若确需清理，先列出对象、保存恢复副本并取得明确确认。
6. 导出仅输出用户选择的普通文本快照；导入明确创建普通便签，不自动关联源账号。

第一期仅创建新的任务便签，避免普通便签转绑定所需的云文件迁移。多 Mac 的位置、颜色和绑定各自管理；需要共享这些本地属性时另立需求。
